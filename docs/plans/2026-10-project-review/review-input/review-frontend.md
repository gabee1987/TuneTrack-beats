## 2. Findings

Format: **ID · Priority · title** — evidence — why it matters — suggested fix.

### A. Rendering performance

**A1 · P2 · GamePage memo wrappers are defeated by handler identity on every `state_update`.**
`pages/GamePage/hooks/useGamePageActions.ts:97-132` — every handler is `useCallback(..., [ …, roomState, … ])`, so a new function is created on each socket update. `components/GamePageHeader.tsx:235-241` and `components/GamePageActionPanels.tsx:215-240` compare those handlers (and `roomState`) by reference, so both `memo` comparators return `false` on every update. The hook already holds `roomStateRef` (line 48); handlers should read from the ref and depend only on stable inputs. Then the comparators can compare the specific `roomState` slices they render (players, `settings.ttModeEnabled`, `turn.turnNumber`, `status`, `hostId`), which is the cheap version of Doc 03 §7.

**A2 · P2 · `TimelinePanelItems` / `TimelineSortableItem` memo is defeated on the hottest path.**
`components/TimelinePanel.tsx:59-76` builds `itemsModel` as a fresh object every render and passes inline lambdas `onCardInfoRequest={(card) => …}` (line 270) and `onPreviewCardRef={(node) => …}` (lines 272-275); `hintAnchorRef={setTimelineCardHintAnchor}` is stable but the other two are not. `components/TimelinePanelItems.tsx:36-39` `useMemo([model, …])` therefore recomputes all view models each render, and `TimelineSortableItem` (`memo`, line 183) receives a new `previewCardRef` lambda (`TimelinePanelItems.tsx:74-80`) and a new `onCardInfoRequest` every time. During a drag, `onSelectSlot` (`useTimelinePanelDragState.ts:187`) updates controller state on each reorder, so the whole timeline re-renders per reorder step. Fix: memoise `itemsModel` on its scalar inputs, hoist the three callbacks with `useCallback`/refs.

**A3 · P2 · Per-consumer viewport listeners (Doc 03 §4).**
`hooks/usePageLayoutMode.ts:26-37` registers `resize` per call site (GamePage, GamePageHeader, TimelinePanel, LobbyPage, HomePage at least); `components/ActionDock.tsx:14-40` `useMobileControlPortalTarget` registers `resize` + `orientationchange` + `matchMedia change` per dock (TurnActionDock and ChallengeActionPanel each call it); `features/hints/HintBubble.tsx:37-38` adds a capture-phase `scroll` listener while visible. On iOS the address-bar collapse fires `resize` continuously; every one of these does `setState`. One `useSyncExternalStore`-backed viewport store notifying only on _mode_ change is the fix the plan already describes.

**A4 · P2 · `--app-height` written from JS overrides the CSS `100dvh` value and thrashes on iOS.**
`main.tsx:7-8,39` sets `--app-height` to `innerHeight` px on every `resize`, which overrides the `@supports (height: 100dvh)` value in `app/styles/globals.css:179-183`. Consumers (`AppRoutes.tsx:45`, `PageTransition.tsx:27`, `LobbyPageMobile.module.css:14`, `PlayPage.module.css:14`, …) therefore get a pixel value that changes during scroll, which causes layout on every resize tick. Prefer `100dvh`/`100svh` in CSS and drop the JS writer, or coalesce through the viewport store and write only on change (Doc 03 §4.2).

**A5 · P2 · Always-on 1 s playback interval and whole-object context value (Doc 03 §5).**
`hooks/useSpotifyPlaybackSdk.ts:521-530` ticks every second whenever `enabled`; `hooks/useHostPlayback.ts:364-389` returns a new object literal every render, so the context value changes every tick. Impact is contained today because the only consumer is `gameMenu/PlaybackTabContent.tsx:19-20`, but the timer runs for the whole game while the menu is closed. Gate the interval on a progress subscriber and `visibilitychange`.

**A6 · P2 · Global capture-phase `pointerdown` listener for the whole game (Doc 03 §6).**
`hooks/HostPlaybackProvider.tsx:75`. Runs `activateElement()` on every touch, including each drag step. Arm on bounded gestures instead.

**A7 · P2 · Drag move does layout reads per event.**
`hooks/useTimelinePanelDragState.ts:52-54` `getComputedStyle(container).display` is called twice per move (lines 166 and 230) and `querySelectorAll("[data-timeline-card='true']")` once per move (line 164); `getBoundingClientRect` per card per move (lines 64, 99). Resolve layout mode and cache the node list on `onDragStart`.

**A8 · P2 · `useTimelineOverflowState` re-creates a `ResizeObserver` whenever `orderedItemIds` changes.**
`hooks/useTimelineOverflowState.ts:14-42` depends on `dependencyKey` (`orderedItemIds`, a new array each reorder), so every reorder step disconnects and re-observes, and calls `getComputedStyle` (line 22). Observe once; read the layout mode from the viewport store.

**A9 · P2 · `GamePageMobile`/`GamePageDesktop` wrap the timeline in a framer `layout` container.**
`mobile/GamePageMobile.tsx:20-24`, `desktop/GamePageDesktop.tsx:20-24`, and `components/ActionDock.tsx:72` (`layout`). `layout` makes framer measure the element every commit; given A1/A2 that is every socket update and every drag step. It also contradicts "animate `transform` and `opacity` only" in spirit, because layout animations are driven by measured size deltas. Remove unless a specific state change needs it; if kept, scope to that change.

**A10 · P3 · No-op memo.** `features/app-shell/components/AppShellMenuDialog.tsx:31` `useMemo(() => tabs, [tabs])`.

**A11 · P3 · `disabledTimelineSlots: []` literal.** `hooks/useGamePageDisplayState.ts:158` returns a fresh empty array each render (new identity for `interaction.disabledSlotIndexes`). Use a module-level constant.

**A12 · P3 · Two 250 ms / 1 s countdown intervals.** `hooks/useChallengeCountdownLabel.ts:18` (250 ms) and `components/TurnActionDock.tsx:40` (1 s) — both cleaned up correctly; acceptable, but note they are the only legitimate periodic timers the game page should have once A5 is fixed.

### C. Motion

**C1 · P1 · `height` is animated in shared motion tokens.** `features/motion/coreMotionTokens.ts:85-97` `createDisclosurePanelMotion` and `features/motion/lobbyMotionTokens.ts:13-28` `createMeasuredDisclosureMotion` animate `height`; used at `pages/LobbyPage/components/LobbyHostTtSettings.tsx:155-160`. `design_system.md` §5: "Never `width`, `height`, `margin`, `top`, `left`". Replace with a clip/translate pattern (`clip-path` or `scaleY` on a wrapper plus opacity), or an `AnimatePresence` mount with a fixed-height skeleton.

### E. State and networking

**E1 · P1 · `emitAction` assumes `crypto.randomUUID` exists.** `services/socket/emitAction.ts:24` calls `crypto.randomUUID()` unguarded. It is only defined in secure contexts; the project explicitly supports plain-HTTP LAN play (`services/socket/resolveServerUrl.ts:27` returns `http://<lan-ip>:3001`, and `docs/operations/deploy-self-hosted.md` discusses the HTTP problem). On `http://192.168.x.x` every gameplay action throws, is caught by the action hooks (`useGamePageActions.ts:124-127`) and surfaces as a generic "failed" with no diagnosis. `services/session/sessionId.ts:25-33` already has the correct fallback (`createSessionId(window.crypto)`); reuse it. Over HTTPS (the deployed path) this does not reproduce.

**E2 · P2 · Offline/rejected actions reset to `idle` silently.** `useGamePageActions.ts:122` `setPlaceCardActionStatus(result.status === "timeout" ? "failed" : "idle")` — `"offline"` and `"rejected"` both go back to `idle`, with no toast. Combined with D4 the user has no way to tell a dropped socket from a slow server. `emitAction` already distinguishes the cases; map `offline` to a visible state.

**E3 · P2 · Socket client: good, one gap.** `services/socket/socketClient.ts` correctly guards concurrent resets (generation counter, lines 29-45), drops the send buffer on reset (lines 22-27), lazy-imports `socket.io-client` (line 31). Listener registration/cleanup is centralised per page hook with `isDisposed` guards (`useGameRoomConnection.ts:127-158`, `useLobbyRoomConnection.ts:222-255`, `features/rooms/useRoomDirectory.ts`, `pages/JoinRoomPage/hooks/useJoinRoomPreview.ts`) — no leaks found. Gap: `useSpotifyPlaybackSdk.ts:506-518` registers `RoomClosed` on the socket from inside a hook that is not a connection hook (rule 12: subscriptions attached in one clear place).

**E4 · P2 · `useGameRoomConnection` effect depends on `navigate`.** `useGameRoomConnection.ts:159` `[navigate, playerSessionId, rememberedDisplayName, roomId]`. React Router's `navigate` identity changes with `location.pathname`; same-path `state`-only navigations (menu open/close, playlist editor) keep it stable, so this is currently safe, but it is fragile: any future pathname change while the page is mounted re-runs the connect/`JoinRoom` emit. Keep `navigate` in a ref like `translateRef`.

**E5 · P3 · Saved playlists service is well-formed.** `services/savedPlaylists/savedPlaylists.ts` validates on read, drops corrupt stores, caps at `MAX_SAVED_PLAYLISTS`, and is injectable. Data-minimisation note: it persists `artworkUrl`/`previewUrl` (third-party Spotify URLs) on the device; acceptable for a local MVP, but should be in the account-backed storage design review when that lands.

**E6 · P3 · Session identity is mirrored to two storages by two modules.** See D7. Also `playerSession.ts` does not wrap storage access in `try/catch` while `playerProfile.ts`, `hintState.ts` and `roomEventToast.ts` do; in a private-mode Safari session with storage disabled, `getOrCreatePlayerSessionId` throws inside `useMemo` (`useGamePageController.ts:31`) and the game page crashes. Low likelihood, but cheap to harden and inconsistent with the sibling services.

### F. Mobile robustness

**F1 · P2 · Viewport height.** Mixed strategies: `--app-height` (JS pixel value, A4), `100svh` (`GamePageMobile.module.css:2-3,12`), `100dvh` (`gamePageChrome.module.css:2`, `GamePageDesktop.module.css:2`, `HomePageMobile.module.css:34`), `100vh` (`spotifySetupShell.module.css:67`). Good.

**F5 · P3 · Audio autoplay.** The SDK unlock on first gesture exists (A6) and the free-tier `<audio>` path is correctly torn down (`useHostPlayback.ts:88-116`). The remaining gap is the ambient listener design, covered by A6.
